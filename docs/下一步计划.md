## 二、后续重构核心架构原则

后续重构应围绕三层架构推进：

### 1. 数据层：Resource

静态配置数据尽量使用 Godot `Resource` 保存，不继续在脚本中硬编码 Dictionary。

适合 Resource 化的数据包括：

- 角色数据
- 敌人数据
- 技能卡数据
- 模组数据
- 状态/Buff 数据
- 遭遇配置
- 奖励池配置
- 单位头像、立绘、图标等资源引用

数据层只描述“是什么”，不负责 UI 展示，也不处理战斗流程。

示例：

- `resources/characters/ranger.tres`
- `resources/enemies/bandit_bruiser.tres`
- `resources/skills/precise_strike.tres`
- `resources/modules/pierce_module.tres`
- `resources/encounters/elite_bandits.tres`

### 2. 表现层：Scene / Node

UI 结构和可视化表现尽量用 `.tscn` 场景搭建，不依赖脚本一层层手工创建复杂节点。

适合组件化的场景包括：

- `battle_unit_view.tscn`
- `battle_board_view.tscn`
- `skill_card_item.tscn`
- `module_item.tscn`
- `skill_grid_view.tscn`
- `skill_preview_panel.tscn`
- `character_loadout_panel.tscn`

表现层只负责：

- 显示数据
- 播放动画
- 展示图片
- 展示状态图标
- 处理 hover / click 等输入
- 通过 signal 把输入事件交给逻辑层

表现层不负责：

- 伤害结算
- Buff 结算
- 敌方 AI
- 奖励规则
- 战斗流程推进

### 3. 逻辑层：GDScript System

规则、流程、计算、状态变化应进入独立 System 脚本，而不是堆在页面脚本中。

候选 System 包括：

- `battle_system.gd`
- `damage_system.gd`
- `status_system.gd`
- `enemy_ai_system.gd`
- `skill_build_system.gd`
- `reward_system.gd`
- `encounter_system.gd`

逻辑层接收 Resource 数据和运行时状态，输出结果给表现层刷新。

### 4. 三层协作原则

- 静态数据不写死在脚本里。
- UI 结构不靠脚本手搓。
- 数量、列表、棋盘格、单位实例可以由代码生成。
- 数据用 Resource 存。
- 结构用 Scene 搭。
- 规则用 GDScript System 管。
- Scene 不承载规则结算。
- System 不直接依赖具体 UI 节点。
- Resource 不处理复杂流程，只保存配置、资源引用和必要的基础校验。

## 三、当前仍存在的不规范问题

### 1. `battle_scene.gd` 仍然过长

虽然显示文本已经基本分离，但该脚本仍同时承担：

- 战斗状态机
- 回合推进
- 玩家行动
- 敌方 AI
- 敌人生成
- 召唤逻辑
- 状态/Buff 结算
- 伤害计算
- UI 刷新
- 日志生成
- 奖励与探索流程跳转

这违反了高内聚、低耦合的维护目标。后续应拆分为多个职责清晰的模块。

### 2. 敌人与遭遇数据仍硬编码在脚本中

敌人名称已经 key 化，但敌人的数值、站位、遭遇组合、召唤池仍写在 `battle_scene.gd` 中。

后续应优先外置为 Resource，以便：

- 调整数值不需要改战斗脚本。
- 新增敌人或遭遇不需要触碰 UI 与状态机。
- 后续支持多章节、多地图、多难度。
- 后续给敌方单位配置头像、立绘、图标等表现资源。

### 3. 文本 key 缺少统一命名规范文档

当前已存在大量 key，例如：

- `UI_*`
- `BUILD_*`
- `BATTLE_*`
- `BATTLE_UI_*`
- `BATTLE_LOG_*`
- `BATTLE_REASON_*`
- `ENEMY_*`
- `ENCOUNTER_*`
- `STATUS_*`

虽然当前命名基本可读，但尚未形成正式规范。后续需要明确：

- key 前缀适用范围。
- UI、日志、数据名、说明文本如何分类。
- 是否允许复用 key。
- key 废弃和重命名流程。

### 4. `.tscn` 中可能仍有未迁移文本

当前重点处理了主流程和 `battle_scene.gd`，但仍需要全项目扫描 `.tscn`：

- 是否还有中文 `text = "..."`
- 是否还有直接显示 key 但脚本未初始化的 Label/Button
- 是否有旧 demo 场景残留

这一步需要和“废弃资产清理”一起做，避免迁移已经不会使用的旧场景。

### 5. 状态/Buff 系统仍只是局部整理

持续状态已经从中文 name 判断改为 `id + name_key`，但完整 Buff 系统仍未模块化。

当前仍存在：

- 层数状态和持续状态分开处理。
- 状态效果说明分散在 `battle_scene.gd`。
- 状态叠加规则写在战斗脚本内部。
- 状态生命周期和 UI 显示没有独立边界。

后续应提取独立状态系统或状态数据库。

### 6. 敌方 AI 与战斗结算耦合

敌方行动逻辑直接写在 `_run_enemy_action()` 和相关函数中。随着敌人类型增加，该函数会继续膨胀。

后续应考虑：

- 按 role 分发到独立策略函数或策略表。
- 将敌方行动描述、目标规则、数值倍率外置。
- 将 AI 选择和伤害结算解耦。

### 7. 奖励、探索、战斗耦合

`battle_scene.gd` 中仍直接处理：

- 战斗胜利后的金币奖励
- 模组奖励
- 遗物奖励
- 探索结束
- 返回构筑/地图
- boss 通关

这些更适合放入探索/奖励流程模块，战斗场景只上报战斗结果。

### 8. 调试资产和废弃资产缺少清理规范

本次删除了 `skill_test_scene`，但项目中仍可能存在旧 demo、旧测试场景、编辑器缓存引用或历史文档引用。

后续需要建立判断标准：

- 当前主流程是否引用。
- 是否仍有文档要求保留。
- 是否属于手动测试工具。
- 是否需要移入 `deprecated` 或直接删除。

### 9. `skill_build.gd` 仍有进一步拆分空间

`skill_build.gd` 当前仍混合了多种职责：

- 技能卡列表展示
- 模组库存展示
- 拼图网格交互
- 模组旋转和放置
- 技能预览
- 角色装备栏
- 页面级流程控制
- 文本格式化和样式初始化

后续应将其逐步组件化，让主脚本变成页面协调器。

建议优先拆分：

- 技能卡列表组件
- 模组库存列表组件
- 技能拼图棋盘组件
- 技能预览组件
- 角色装备栏组件

### 10. 战斗单位缺少独立表现层

后续计划给场上我方角色和敌方单位加入图片显示。当前 `battle_scene.gd` 仍通过代码动态创建棋盘格和单位文字，后续继续增加图片、动画、状态图标、受击反馈会很难维护。

建议建立通用单位视图场景：

- `scenes/ui/battle_unit_view.tscn`
- `scripts/ui/battle_unit_view.gd`

该场景负责：

- 显示头像、立绘或图标。
- 显示名字、HP、护盾、速度。
- 显示状态图标。
- 显示阵营样式。
- 处理 hover、click、选中、高亮等输入表现。

不建议一开始给每个角色和敌人都创建独立 `.tscn`。更合理的方式是：

- 先做一个通用 `battle_unit_view.tscn`。
- 角色和敌人 Resource 提供图片、名字 key 和数值。
- 需要特殊表现的 boss 或召唤标记再考虑派生场景。
