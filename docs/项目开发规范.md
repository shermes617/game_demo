# Godot 项目 Codex 开发规范提示词

你现在要协助我开发一个 Godot 项目。请严格遵守以下规范。

本项目的目标不是只让当前功能“能跑”，而是要保证工程结构清晰、代码可维护、功能可扩展、数据可调整、文本可翻译，并且便于使用 Git 回滚和管理版本。

在任何修改前，请先阅读相关文件、理解现有结构、输出实现计划，等待我确认后再修改。不要直接上来就改代码。

---

# 1. 总体开发原则

本项目遵循以下核心原则：

1. 固定结构用 `.tscn` 场景搭建。
2. 可复用对象做成独立 `.tscn` 场景。
3. 动态数量对象用代码实例化已有 `PackedScene`，不要从零用代码搭建复杂 UI。
4. 代码以解耦为核心，避免单个脚本过长、职责混乱、相互强依赖。
5. 数据和代码分离。不可变数据、平衡数据、翻译文本、显示文本不要硬编码在 `.gd` 脚本中。
6. UI 只负责显示、输入和信号转发，不负责复杂业务规则。
7. 核心规则放在独立系统或规则模块中。
8. 修改前先判断是否需要新建脚本、场景、Resource 或数据文件。
9. 修改后检查代码结构是否简洁、职责是否清晰、是否符合解耦要求。
10. 大改动前提醒我先新建 Git 分支或提交稳定版本。

# 2. 场景与节点规范

## 2.1 固定结构优先使用 `.tscn`

固定存在的界面、容器、布局、组件，必须优先在 Godot 编辑器中做成 `.tscn` 场景。

例如：

```txt
SkillBuildScene.tscn
BattlePrepareScene.tscn
BattleScene.tscn
MapScene.tscn
CharacterPanelView.tscn
SkillCardView.tscn
RelicIconView.tscn
BattleUnitView.tscn
```

不要在正式功能中大量使用代码从零搭建完整 UI 树。

不推荐：

```gdscript
var panel := Panel.new()
var title := Label.new()
var button := Button.new()
panel.add_child(title)
panel.add_child(button)
```

推荐：

```gdscript
var view := preload("res://ui/skill/SkillCardView.tscn").instantiate()
view.setup(skill_data)
container.add_child(view)
```

## 2.2 可复用对象必须拆成独立场景

如果某个对象满足以下任意条件，应优先拆成独立 `.tscn`：

1. 会重复出现。
2. 有多个子节点。
3. 未来可能复用。
4. 有独立显示逻辑。
5. 需要在 Godot 编辑器中调整布局或样式。
6. 用代码创建时需要超过大约 5 个 UI 节点。
7. 不是临时调试内容。

例如：

```txt
SkillCardView.tscn
ModuleSlotView.tscn
CharacterSlotView.tscn
RelicIconView.tscn
BattleUnitView.tscn
MapNodeView.tscn
TooltipView.tscn
```

## 2.3 什么时候允许动态生成节点

只有以下情况可以用代码动态创建节点：

1. 临时调试信息。
2. 极小型、一次性的辅助节点。
3. 数量动态但结构极简单的对象。
4. 明确说明不需要复用和维护的实验代码。

正式功能中，动态列表应该实例化已有 `.tscn` 模板，而不是从零创建一堆 `Button.new()`、`Label.new()`、`Panel.new()`。

# 3. 代码解耦规范

## 3.1 避免“上帝脚本”

不要把大量功能塞进一个脚本中。

禁止把以下职责混在同一个脚本里：

```txt
UI 创建
按钮响应
技能数据读取
伤害计算
回合推进
敌人 AI
遗物触发
动画播放
场景跳转
存档读写
```

如果一个脚本同时承担太多职责，必须考虑拆分。

每个脚本的职责应该可以用一句话说清楚。

例如：

```txt
DamageCalculator：根据攻击方、防御方和技能计算最终伤害。
SkillCardView：显示一张技能卡，并把点击事件向外发送。
RelicTriggerSystem：在指定时机检查并触发遗物效果。
BattleManager：维护战斗状态，并协调回合、技能、遗物等系统。
```

如果一个脚本的职责描述变成：

```txt
负责战斗、UI、技能、遗物、角色、动画和场景跳转
```

说明它已经需要拆分。

# 4. 独立模块与链接模块

本项目代码分为两类：

1. 独立模块
2. 链接模块

## 4.1 独立模块

独立模块负责单一、明确、可复用的功能。

要求：

1. 职责小而专注。
2. 尽量不依赖场景树。
3. 尽量不直接引用 UI 节点。
4. 尽量不直接引用其他具体模块。
5. 优先通过参数输入数据，通过返回值、结果对象或信号输出结果。
6. 可以替换。
7. 可以复用。
8. 复杂度低。
9. 不负责组织完整游戏流程。

适合做成独立模块的例子：

```txt
DamageCalculator.gd
SkillCostCalculator.gd
MoraleCalculator.gd
TargetSelector.gd
RelicConditionChecker.gd
ModuleEffectResolver.gd
RewardGenerator.gd
```

独立模块应该尽量像这样：

```gdscript
func calculate_damage(attacker_data, defender_data, skill_data) -> int:
	var base_damage = skill_data.base_damage
	var final_damage = base_damage + attacker_data.attack - defender_data.defense
	return max(final_damage, 0)
```

不应该像这样：

```gdscript
func calculate_damage():
	var enemy = get_node("../Enemy")
	var label = get_node("../UI/DamageLabel")
	enemy.hp -= 8
	label.text = "造成8点伤害"
```

## 4.2 链接模块

链接模块负责组织流程，连接多个独立模块。

链接模块可以知道多个模块的存在，但不应该把所有具体规则都写在自己内部。

适合做链接模块的例子：

```txt
BattleManager.gd
TurnManager.gd
SkillResolver.gd
RelicTriggerSystem.gd
GameFlowController.gd
SceneTransitionController.gd
SystemConnector.gd
```

链接模块负责类似流程：

```txt
玩家点击技能
→ UI 发出信号
→ BattleManager 接收请求
→ SkillResolver 结算技能
→ DamageCalculator 计算伤害
→ RelicTriggerSystem 检查遗物
→ BattleManager 更新战斗状态
→ UI 接收信号并刷新显示
```

## 4.3 依赖方向

尽量保持以下依赖方向：

```txt
Data / Resource
	↑
Rules / Calculators / Checkers
	↑
Systems / Managers / Controllers
	↑
Views / UI
```

实际运行时：

```txt
UI 把玩家输入交给 Manager
Manager 调用独立模块
独立模块返回结果
Manager 更新状态
Manager 发信号通知 UI
UI 刷新显示
```

避免：

```txt
DamageCalculator 直接改 UI
RelicData 直接调用 BattleManager
SkillCardView 直接操作敌人血量
BattleUnitView 直接结算技能效果
系统 A 调用系统 B，系统 B 又反过来调用系统 A
```

# 5. 判断是否新建脚本

在生成或修改代码前，必须先判断：

1. 这个功能属于数据、规则、流程、表现中的哪一层？
2. 是否应该新建独立脚本？
3. 是否会让现有脚本职责变多？
4. 是否存在更小的可复用模块？
5. 哪个模块负责连接这些逻辑？
6. 新代码是否直接依赖 UI 节点或场景树？
7. 有没有双向引用或循环引用风险？
8. 修改后单个脚本是否过长？
9. 是否应该通过 Resource 或数据文件驱动，而不是写死在代码中？

## 5.1 应该新建独立脚本的情况

满足以下任意条件，应考虑新建独立脚本：

1. 逻辑可能被多个地方复用。
2. 逻辑和当前脚本主要职责不同。
3. 逻辑可以独立测试。
4. 逻辑超过约 50 到 100 行，并且还会继续增长。
5. 逻辑包含明确的规则计算。
6. 逻辑不应该依赖 UI 节点。
7. 未来可能替换成另一套规则。
8. 当前脚本已经开始变得冗长。

## 5.2 可以留在原脚本的情况

以下情况可以留在原脚本中：

1. 只服务当前场景的简单显示逻辑。
2. 只有几行的按钮响应。
3. 只负责把数据填到 Label、TextureRect、Button。
4. 只属于某个 UI 组件内部的小逻辑。

例如：

```gdscript
func set_title(text: String) -> void:
	title_label.text = text
```

这种不需要拆成独立模块。

# 6. 数据与代码分离规范

## 6.1 禁止硬编码显示文本

不要在 `.gd` 脚本中硬编码中文显示文本。

不推荐：

```gdscript
skill_name_label.text = "火焰打击"
skill_desc_label.text = "造成8点伤害，并施加燃烧"
```

推荐：

```gdscript
skill_name_label.text = tr("SKILL_FIRE_STRIKE_NAME")
skill_desc_label.text = tr("SKILL_FIRE_STRIKE_DESC")
```

或者：

```gdscript
skill_name_label.text = TextDatabase.get_text("SKILL_FIRE_STRIKE_NAME")
skill_desc_label.text = TextDatabase.get_text("SKILL_FIRE_STRIKE_DESC")
```

代码中只保留文本 key，真正的中文和其他语言翻译放在外部文件中。

## 6.2 需要外置的数据

以下内容不要硬编码在 `.gd` 脚本中：

```txt
技能名称
技能描述
遗物名称
遗物描述
角色名字
敌人名字
剧情文本
按钮显示文本
教程文本
提示文本
错误提示
平衡数值
关卡配置
敌人属性
掉落表
翻译内容
```

## 6.3 翻译文本

显示文本统一放入：

```txt
res://localization/localization.csv
```

示例格式：

```csv
key,zh,en
UI_START_GAME,开始游戏,Start Game
UI_BACK,返回,Back
SKILL_FIRE_STRIKE_NAME,火焰打击,Fire Strike
SKILL_FIRE_STRIKE_DESC,造成8点伤害，并施加燃烧,Deal 8 damage and apply Burn
RELIC_ZERO_ENERGY_NAME,空能余烬,Zero-Energy Ember
```

代码中使用：

```gdscript
tr("UI_START_GAME")
tr("SKILL_FIRE_STRIKE_NAME")
tr("SKILL_FIRE_STRIKE_DESC")
```

如果项目已经使用自定义 `TextDatabase`，则通过统一文本数据库读取。

## 6.4 平衡数据和配置数据

技能、模组、遗物、敌人、角色等配置数据，优先放在：

```txt
Resource / .tres
JSON
CSV
```

不要大量硬编码在 `.gd` 中。

例如技能数据应包含：

```txt
id
name_key
desc_key
cost
base_damage
tags
icon
allowed_modules
```

而不是：

```gdscript
var skill_name = "火焰打击"
var skill_desc = "造成8点伤害"
var damage = 8
```

推荐：

```txt
id: fire_strike
name_key: SKILL_FIRE_STRIKE_NAME
desc_key: SKILL_FIRE_STRIKE_DESC
cost: 2
base_damage: 8
```

显示时：

```gdscript
name_label.text = tr(skill_data.name_key)
desc_label.text = tr(skill_data.desc_key)
```

## 6.5 文本和数值分离

不要把文本描述和数值逻辑混在一起。

不推荐：

```json
{
  "name": "火焰打击",
  "description": "造成8点伤害",
  "damage": 8
}
```

推荐：

```json
{
  "id": "fire_strike",
  "name_key": "SKILL_FIRE_STRIKE_NAME",
  "desc_key": "SKILL_FIRE_STRIKE_DESC",
  "damage": 8,
  "cost": 2
}
```

如果将来需要动态描述，可以使用模板 key，例如：

```csv
key,zh,en
SKILL_DAMAGE_DESC,造成{damage}点伤害,Deal {damage} damage
```

再由代码填充参数。

## 6.6 编码要求

所有文本文件必须保持 UTF-8 编码。

包括：

```txt
.gd
.tscn
.tres
.csv
.json
.md
```

禁止使用 GBK、ANSI 或系统默认编码保存项目文件。

修改中文文本时必须小心，不要重写、破坏或重新编码已有中文内容。

# 9. UI、数据、规则、流程分层

## 9.1 数据层

数据层负责描述“这个东西是什么”。

例如：

```txt
技能名称 key
技能描述 key
基础能量消耗
基础伤害
技能标签
模组槽位
遗物触发时机
敌人基础属性
角色基础属性
```

数据层不要直接操作 UI 节点，不要直接控制战斗流程。

## 9.2 表现层

表现层负责“这个东西怎么显示”。

例如：

```txt
SkillCardView
RelicIconView
BattleUnitView
CharacterPanelView
```

表现层可以提供：

```gdscript
func setup(data) -> void:
	...
```

表现层不要写复杂战斗规则。

## 9.3 规则层

规则层负责“规则怎么计算”。

例如：

```txt
伤害计算
费用计算
目标筛选
士气变化
遗物触发条件判断
模组效果计算
```

规则层尽量不依赖场景树和 UI 节点。

## 9.4 系统层

系统层负责“流程怎么组织”。

例如：

```txt
回合推进
技能结算流程
遗物触发流程
战斗状态维护
背包状态维护
奖励流程
```

系统层可以调用规则层，但不要把所有规则都写死在系统层里。

## 9.5 流程层

流程层负责“场景和游戏阶段如何切换”。

例如：

```txt
主菜单 → 技能构筑 → 战斗准备 → 战斗 → 奖励 → 地图
```

场景跳转、流程推进不要散落在多个 UI 脚本中。

```txt

.tres
.res
.import
project.godot
```

要求：

1. 不要无意义地重写整个 `.tscn` 或 `.tres` 文件。
2. 如果只是修改逻辑，不要顺手重排场景文件。
3. 修改 `project.godot` 前必须说明具体原因。
4. 不要删除或破坏 Godot 的 UID、资源路径、节点路径、场景引用。
5. 如果需要移动或重命名资源，必须说明会影响哪些引用文件。
6. 修改后要说明如何在 Godot 中检查场景是否仍能打开。
